## 2. 三种产品路线

| 路线 | 优点 | 代价 | 结论 |
|---|---|---|---|
| A：采用 GSD Pi 一类统一运行入口 | 已有较完整的新会话执行与状态管理 | 改变用户工作入口，不能直接满足三个原客户端内的体验 | 若用户接受统一入口，优先评估 |
| B：共享交接 skill + 适配层，扩展现有控制器 | 保留原客户端；复用循环与任务基础设施 | 三种生命周期/窗口接口仍需做适配 | **当前推荐方向**；以 P0 结果决定基座 |
| C：只写 skill 或复制几份提示词 | 部署简单、易移植 | 自动触发、进程控制、交接原子性都缺乏确定保证 | 仅提供手动/辅助模式，不能宣称完整实现 |

独立自研控制器是 B 的后备方案。只有候选基座无法满足关键不变量，或者改造量明显大于最小核心时才选择。是否采用不能用主观“感觉很轻”决定，要提交功能探针与差距报告。

## 3. Codex

### 已确认

- 官方 hooks 文档提供 `PreCompact`、`PostCompact`、`SessionStart`、`Stop`、`Interrupt` 等事件；配置存在精确定义的信任要求。`Stop` 的继续同一会话与新建会话不同。新版本事件语义不可假定适用于所有旧版本。[Codex Hooks](https://learn.chatgpt.com/docs/hooks)
- app-server 提供 `thread/start`、`turn/start`、`turn/steer`、`turn/interrupt`；`thread/fork` 复制历史。可获得 token usage 和 compaction 相关事件，适合控制器建立新 thread。该接口及部分传输/字段包含实验状态，应固定版本并做契约验证。[Codex App Server](https://developers.openai.com/codex/app-server)
- 本机只读确认 CLI 为 `0.144.4`；帮助文本含 app-server、stdio、daemon/proxy 和 schema 生成入口。**未运行实际会话验证。**
- 当前 Codex 桌面任务暴露 `create_thread`、`send_message_to_thread`、`read_thread`、`wait_threads` 等宿主工具；这只能证明本会话有这些能力，不等于外部便携工具可以调用同名 API。

### 建议适配

控制器优先连接自己管理的 app-server；通过 hooks/事件掌握进度，在旧 turn 静止后创建新 thread，再提交接手材料。读取有效配置，显式保持 model/provider/effort/cwd/权限与工具环境，不能假定 app 或 CLI 的默认值等于旧会话的值。

### 必须验证的边界

1. 桌面 App 如何连接或呈现控制器创建的 thread；是否可观察、选择、继续，而非仅后台生成日志。
2. 当前桌面内置 runtime 与全局 CLI 可能版本不同，需要分别报告。
3. 能否接管已运行的会话，而非只能管理由控制器启动的新任务。
4. hook 是否被启用并信任、压缩事件是否完整、effective model 是否可读。
5. Windows 下具体传输和失联重连行为；不依赖直接改写内部数据库。

## 4. Claude Code

### 已确认

- `SessionStart`、`PreCompact`、`PostCompact`、`Stop` 等 hooks 可作为入口。当前官方文档中，`PreCompact` 可阻止压缩，但在已触发上下文错误的恢复路径上阻止它可能导致请求失败；不适合作为唯一交接策略。SessionStart 的 model 字段也可能缺省。[Hooks reference](https://code.claude.com/docs/en/hooks)
- CLI 支持程序化调用和结构化输出；`--resume` / `--continue` 用于旧会话恢复。新会话应使用新的调用/明确的 session ID，而不是误用 resume。模型参数和 session 参数以安装版本的 CLI reference 为准。[程序化运行](https://code.claude.com/docs/en/headless)、[CLI reference](https://code.claude.com/docs/en/cli-reference)
- 本机版本为 `2.1.270`，未运行模型任务。

### 建议适配

插件/hook 负责捕获原始用户输入和运行事件、注入短交接入口。外部 supervisor 管理 CLI/SDK 会话生命期，以受支持的终端/会话入口呈现新会话。不能把“一直阻止 Stop”当作干净会话轮换。

必须验证父进程退出对孩子进程的影响、终端挂接、SDK 与现有 CLI 登录/配置兼容性，以及有效模型读取和历史会话可见性。初版优先沿用用户已有 CLI 登录方式，不默认要求改为新的 API 计费通道。

## 5. DeepSeek Harness / DSH

### 已确认

本机 `dsh.cmd` 指向 DSH Desktop 活跃 runtime，包为 `@deepseek-ai/dsh@0.1.5-rc.1`，仓库为 `deepseek-ai/deepseek-harness`。本机只读检视了包 README 与类型声明，没有读取 API key、用户私有会话或改写配置。

- DSH 是插件架构，有 SDK stdio 入口、会话事件、压缩组件、skill 与 hook 兼容组件。[官方仓库](https://github.com/deepseek-ai/deepseek-harness)
- SDK 初始化接收 cwd/provider/model/reasoningEffort；`session/prompt` 对新 sessionId 创建 agent/session；可订阅 `session.event` 和 `session.status`。本机协议请求表只有 initialize、session/prompt、shutdown，不能假造一个 per-session cancel API。[SDK 协议](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sdk/protocol/src/types.ts)、[server](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sdk/server/README.md)
- Claude hook bridge 在本机 README 中列出 SessionStart、UserPromptSubmit、Pre/PostToolUse、Stop 和 SubagentStart/Stop；不含 PreCompact/PostCompact。不能因为兼容部分 Claude hooks 就推断压缩 hooks 也兼容。本机包 repository 元数据与官方仓库路径一致。[bridge 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/hooks/hooks-claude-code/README.md)

### 建议适配

优先原生插件订阅会话/压缩生命周期，复用 SDK 或原生 session service 创建根会话。SDK 路线可在进程自然 idle 后交接；若缺少可验证的按会话停止能力，使用独占 worker 进程或补原生插件。不能对共享 DSH runtime 调用 shutdown 来停一个项目。

DSH Web/Desktop 会话显示、选中、状态同步，以及新会话是否能获得相同工具和有效模型，均作为原生入口探针；本次没有启动或操作 DSH Web。

## 7. 复用决策的通过条件

对 Ralph Orchestrator、GSD Pi（统一入口候选）与 DSH 原生 Ralph，使用同一个四单元测试项目，形成三次交接。记录：新旧会话 ID、父子关系、模型配置、原话摘要来源、完成证据、自动轮换、失败重试和用户暂停。

优先扩展 Ralph Orchestrator 的条件：可固定后端/模型、可在轮次前后拦截、可附加交接 ID 和接手确认、可在已确认静止后转交写权、支持当前 Windows 启动方式，且许可与维护成本可接受。不满足关键条件时必须指明具体接口缺口，再选择最小自研核心。

采用现有 GSD/Beads 任务系统时以其为唯一任务状态来源，通过映射引用任务 ID。不要再创建一个需要手工同步的权威 `tasks.json`。本提案技术设计中的任务模型是协议要求，不是强制自建数据库。

## 8. 调研限制

本轮验证到公开文档和静态接口层，不代表已测出可靠性、延迟、成本或效果。源码 main/master 可能与本机候选版本不同；P0 要固定 tag/commit、记录许可、运行最小探针。未核实的原生 UI 能力不会在开发任务中被自动算作已支持。
