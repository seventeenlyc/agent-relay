# 需求与用户原话

版本：提案 v0.1；2026-09-17。文中的“建议”属于设计推断，不是用户已经指定的实现方式。

## 1. 用户原始描述

以下保留本轮用户消息正文，不用后文的解释替换它。

> 我想要一个skill，适配codex、Claude Code和dsh，痛点与需求：
>
> 1. 需要进行长任务时，agent会压缩信息，前几轮的压缩能较好的保留用户的需求和意图，但时间越长，就越容易跑偏，很多时候跑偏了用户还没意识到、或者以为只是目标里需要额外补足的内容，完成后会回归主线。但是实际上，当用户真正发现项目已经被改的面目全非的时候，已经消耗了大量的资源，也很难回退。
> 2. 而如果用户想要在中途停下工作而切换窗口，又很难把控好停下的时间，可能会让完成到一半的工作被另一个全新的窗口接管，导致该部分效果很差。
> 3. 如果用户选择在任务模式下每完成一个任务就换一次窗口，则需要用户经常关注工作的情况，否则可能任务停下很久了才发现。
> 4. 就算用户能把前面的问题手动解决好，但是每次切换窗口，都需要告诉模型总的需求、以及上一次完成到了哪一个部分、规划的任务列表是怎么样的，非常的麻烦。
>
> 所以我希望制作一个skill或者工具，在以上三个agent里实现：
>
> 1. 当信息被压缩多次、任务时间过长、有多个子任务、目标短期内难以实现的时候，按进度停下工作，并把当前的状态、需求、用户的原始描述等信息总结好，并更新记忆。
> 2. 完成以上的整理以后，自动新开一个对话，保持原来的模型，把总结的信息自动发给新窗口，继续进行任务。
> 3. 这个功能每次都会自动触发，而不是要手动的提醒
>
> 你现在需要理解我的需求、查找是否有类似的工具避免重复造轮子、写好开发文档、整理好任务，你暂时不需要帮我实现。

## 2. 需求拆解与验收映射

| ID | 需求 | 可观察的验收结果 |
|---|---|---|
| R1 | 长链路中保持目标与范围 | 经过至少 10 次交接，原话可追溯，所有当前任务关联有效需求；被用户否决的内容不会被后继会话重新实施 |
| R2 | 在合适进度节点停下 | 交接时工作单元已验证完成，或有明确的部分完成恢复记录；不能以模型一句“完成”代替验证 |
| R3 | 进度、状态和记忆自动落盘 | 原话、修正、需求、决策、任务图、工作区变化、证据、下一步都进入一致检查点 |
| R4 | 自动新建会话并投递交接材料 | 新旧 session/thread ID 不同，完整旧会话未被自动复制，新会话无需用户粘贴材料即可启动 |
| R5 | 保持原模型及相关执行环境 | 核对新旧有效 provider/model/reasoning 配置；差异或无法读取必须显式处理 |
| R6 | 每次自动触发，连续推进 | 至少连续 3 次真实自动交接，不需再次输入“继续”；每个后继会话继续受控制器管理 |
| R7 | 用户随时离开、切换或暂停 | 可请求在下一安全节点暂停；用户关闭查看窗口不被误判为任务完成或默认取消 |
| R8 | 三客户端适配 | Codex、Claude Code、DeepSeek Harness 分别提供经过验证的入口与能力说明 |
| R9 | 进度可见、无需盯守 | 展示当前任务、会话链、交接原因、下一步和是否需要用户动作；正常交接不要求点击 |
| R10 | 工作可恢复、可定位回退范围 | 可定位每个任务的工作区基线、变化和验证证据；恢复不能覆盖原有未提交用户修改 |
| R11 | 优先复用现有成果 | 先提交真实试用/差距报告，再决定扩展现有工具或实现最小核心 |
| R12 | 本轮仅调研、文档与任务整理 | 不安装 skill、不改客户端设置、不启动长期执行、不实现产品代码 |

R1 的 10 次、R6 的 3 次是建议的验收阈值；不是用户指定的运行频率。

## 3. 对需求的理解

用户要解决的是长期工作的连续性。会话是可替换的执行载体，任务目标、需求修订和进度应独立于会话保存。换窗口本身无法保证不跑偏；若错误摘要被一代代传递，新窗口仍会继承错误。因此必须同时解决交接机制和目标校验。

“按进度”解释为优先在有明确产物和验证结果的任务边界换会话。时间长或发生压缩只触发交接准备，不默认立刻杀死当前任务。无法及时完成时允许转为可恢复的部分检查点，但不得伪报完成。

“自动触发”解释为用户一次启用后，控制器每轮自行判断、整理、建会话和续跑。不要求用户每轮运行命令；首次启用和客户端本身要求的安装/信任步骤仍需完成。用户明确暂停后，不能靠后台循环自行重启。

## 4. 明确区分的概念

| 概念 | 是否足以满足完整需求 |
|---|---|
| 在原会话压缩上下文 | 不足；会继续依赖摘要，需要目标锚点和校验 |
| fork 旧会话 | 不足；常复制历史，不能当作干净上下文 |
| 新的无历史子 agent | 可用于执行任务，但不能自动算作原生新对话 |
| 新主会话/新 thread | 满足会话分离部分；还需自动投递、模型校验与原界面呈现 |
| 新标签/新对话入口 | 建议作为主要 UI 目标，允许用户查看旧会话链 |
| 新操作系统窗口 | 字面“新窗口”的额外能力，是否强制要求尚待确认 |

## 5. 设计假设与待确认事项

| 编号 | 当前处理 | 对后续工作的影响 |
|---|---|---|
| A1：dsh 身份 | 本机安装包确认是 DeepSeek Harness，按此设计 | 若用户指其他产品，只替换 DSH 适配方案 |
| A2：Codex 入口 | 桌面 App 与 CLI 都保留；分别验收 | 原生桌面可见会话是 P0 探针，不能延后才发现不支持 |
| A3：窗口含义 | 暂按原客户端可见新对话；独立 OS 窗口是可配置展示方式 | 不静默将需求缩减成后台子 agent |
| A4：首次启用 | 可全局自动发现，但具体运行只在选定项目/任务内启用 | 防止无关聊天自动开新窗口 |
| A5：操作系统 | 先确保本机 Windows 路径，再验证 macOS/Linux | 用户未明确跨 OS 发布范围，文档不宣称已跨平台 |
| A6：费用与运行时间 | 允许配置总预算、交接次数、无进展次数 | 不把示例阈值当作用户已授权的消费上限或无限授权 |
| A7：同模型 | 指交接时有效模型和推理设置；不得换成默认值 | 若平台无法读出，需标记未验证，不能宣称精确保持 |

以上未知项不妨碍完成设计文档；它们约束对应实现任务的验收结论。

## 6. 非目标

- 本轮不实现、不安装，不替用户开启自动运行。
- 不自动在三个客户端之间切换模型或账号；首版是在同一客户端内续跑。
- 不替代现有开发方法、不自动重写全部规划、不引入新的产品需求。
- 不保证任意工具调用都能无损中断，也不宣称语义漂移能被百分之百识别。
- 不默认绕过工具权限、不自动提交/推送/发布，不以“无人值守”为由扩大授权。
- 不以不停换会话无限重试来模拟进展。
