# 验收与下一窗口接手说明

版本：提案 v0.1；2026-09-17。这里描述未来测试，不代表产品已经实现或测试通过。

## 1. 最小成功演示

在独立测试项目中给出一个有四个工作单元、明确禁止项的需求，只启用一次。系统自动完成第一单元，形成检查点，启动相同模型的新会话，自动接手；经三次交接完成四个单元，最后一个单元完成后不为凑数再建会话。用户无需发“继续”，能在各自原客户端看见新旧会话和进度。

每端记录：版本、启动入口、模型 requested/effective 值、会话 ID、继承上下文的方式、原话/修订哈希、检查点和 ACK、执行权 epoch、产物/验证证据、交接耗时、通知与人工操作次数。

Codex App 与 CLI 分开记录；Claude Code 记录终端/会话呈现方式；DSH 记录 Web/Desktop 根会话可见性。只产生无历史子 agent 的演示标为 L2，不冒充 L3。

## 3. 故障注入位置

至少覆盖：记录交接意图前后、旧工具结束前后、文件快照写入中、数据库发布前后、outbox 投递前后、创建回包丢失、只读接手中、ACK 接收后、owner CAS 后、继续令牌发送后、第一条写操作后。

每次重启核对不变量：最多一个授权写入者；没有半写检查点；没有丢失用户修订；没有重复完成/外部动作；暂停/取消仍有效。对数据库与文件之间的提交窗口，分别验证“孤立文件”与“无效引用”处理。

## 4. 防漂移对照评测

准备同一任务集的三个条件：

1. 原生长会话持续工作，由客户端自然压缩。
2. 每阶段新会话，但只传递上一份摘要。
3. 本方案：原话与修订账本、需求/证据检查、按单元自动交接。

任务集中包含多阶段代码维护、文档协作和带用户修订的规划，避免只测简单 TODO。使用相同客户端版本、模型配置、工具权限和初始文件；每个条件至少重复 3 次，记录随机性和失败分布。可以用模拟事件测试高频压缩，但必须与真实模型长任务结果分开报告。

| 指标 | 定义 |
|---|---|
| 原话完整性 | 原始消息可恢复且哈希一致的比例 |
| 有效需求覆盖率 | 当前有效验收标准中有产物和有效证据的比例 |
| 越界动作数 | 实际执行、无法关联用户目标且不属于必要补充的动作 |
| 修正遵循率 | 修正生效后，后续相关动作遵循新约束的比例 |
| 接手成功率 | 材料/模型/工作区/下一步一致且可执行的交接次数 / 总次数 |
| 重复执行率 | 已提交任务或外部动作被无依据重复的次数 |
| 自动推进率 | 无用户“继续”命令完成的可执行单元比例 |
| 交接成本 | 停止旧写入至新单元开始的耗时，以及可观测 token/费用 |
| 可恢复性 | 故障后无丢失/覆盖/重复副作用恢复的场景比例 |

语义评分需由独立读者依据用户原话判定，保留争议项，不能仅让生成摘要的模型给自己打分。若完整方案明显增加成本而没有提高需求遵循，应调整策略，不把频繁换窗口本身视作成功。

## 5. 建议发布门槛

- 机械不变量与故障场景必须全部通过；出现双写、丢失用户修正或取消后自启，阻止发布。
- 三端至少连续 3 次真实自动交接（4 个工作单元）；目标链路至少 10 次交接的语义评测（至少 11 个工作单元）。
- 已知模型变化测试中不得静默继续；无法观测的服务端路由限制明确披露。
- 原生 L3 未完成的客户端必须标记为受限，不以 L2 demo 宣传完整支持。
- 接手延迟、token 与费用先实测再定 SLA；本提案不虚构性能保证。

以上是建议门槛；用户若改变入口范围，应修改需求和验收版本，不能删掉失败证据来“通过”。
