# 现有工具同场景评估与差距分析报告 (P0-04)

**评估日期:** 2026-09-17  
**评估目标:** 围绕长任务自动交接的四个核心维度（三端原生适配、原生界面可见、原始需求防漂移、事务级状态机与故障恢复），评估现有开源方案（Ralph Orchestrator、GSD Pi、DSH 原生 Ralph、Beads）的复用可行性与重构代价。

---

## 一、 评估对象概览

| 工具 | 定位与核心能力 | 许可证与维护状态 |
|---|---|---|
| **Ralph Orchestrator** | 专门的多 CLI 后端编排器（支持 Claude Code, Codex CLI 等），提供循环、任务图、看板和 MCP。 | 开源，活跃维护 |
| **GSD Pi (open-gsd/gsd-pi)** | 独立工作流/TUI 入口，自动模式下按单元分配全新会话，从持久状态装配上下文并进行验证。 | 开源（原 GSD 2 迁移后续） |
| **DSH 自带 `dsh-tool-ralph`** | DSH 内部原生插件，前台循环调度全新子 agent，通过共享工作区与结构化报告推进目标。 | 内置于 DSH runtime (0.1.5-rc.1) |
| **Beads (gastownhall/beads)** | 专注依赖关系的任务图与持久项目记忆库，支持与 Codex/Claude 集成。 | 开源，专注任务状态 |

## 三、 深度差距分析

### 1. Ralph Orchestrator
- **优势**：架构设计与 Agent Relay 的思路最为接近，已经抽象了多 CLI 后端，拥有成熟的轮次统计与看板。
- **关键差距**：
  1. **缺失 DSH 支持**：完全没有对接 `@deepseek-ai/dsh-sdk-protocol` 的代码，无法满足国内用户常用的 DeepSeek Harness。
  2. **原生桌面 App 呈现缺失**：其设计初衷是在后台通过 CLI 不断唤起新进程，没有利用 Codex `app-server` 的原生 thread 协议，也没有对接 DSH 的 `$HOME/.dsh/sessions` 原生索引。
  3. **需求原文可追溯性**：采用全局 PRD / 进度文件，多次交接后依然容易被大模型的自生成摘要“逐步稀释”，缺乏“用户原话不可覆写”的防御性数据契约。

### 2. GSD Pi
- **优势**：自动模式成熟，按任务单元切分会话的思想高度契合。
- **关键差距**：
  - GSD Pi 本身是一个**独立的产品入口**。如果强行采用 GSD Pi，用户必须改变现有的工作习惯，放弃 Codex 桌面、Claude Code 终端或 DSH 界面，转而在 GSD 的 TUI 终端中工作。这与用户需求原话（“在以上三个 agent 里实现，原界面可见”）产生直接冲突。

### 3. DSH 自带 `dsh-tool-ralph`
- **优势**：原生内置，开箱即用。
- **致命硬伤（官方文档已确认）**：
  1. 它在 DSH 内部只是一个模型工具（Tool），通过父会话调用 `tool_use: ralph` 并在后台产生一组子 agent。**用户看到的仍然是同一个旧对话卡在 `running` 状态**，不满足用户“自动新开一个对话，按进度停下工作并换窗口”的原生体验。
  2. 官方明确标注：“完成由 worker 自行声明，没有独立评估器；无后台恢复检查点；无预算与耗时控制”。

### 4. Beads
- **定位**：优质的任务依赖图模型。
- **结论**：可以在 Agent Relay 内部作为任务图契约的数据结构参考，但 Beads 本身不是会话调度器，无法独立承担交接重任。

## 四、 最终决策建议 (Decision)

**结论：不整体绑架于任何单一重量级框架，采用“微内核轻量控制器（Agent Relay Core）+ 复用现有优秀模式”。**

### 为什么最小自研核心控制器代价最低、可靠性最高？
1. **P0 探针已彻底打通三端底层协议**：
   - Codex：通过 `app-server --stdio` 的 JSON-RPC，几行代码即可直接创建隔离的 thread。
   - Claude Code：通过 `-p --session-id <uuid> --output-format stream-json` 已经实现完全隔离与高效交互。
   - DSH：通过 `node bin.js --profile sdk` 的标准 JSON-RPC 直接接管会话，并直接落盘至 `$HOME/.dsh/sessions`。
2. **改造成本对比**：
   - 改造 Ralph Orchestrator：需修改其核心调度器以支持 DSH，重构其会话启动逻辑以适配 App-Server，重写其上下文组装层以增加不可变账本，工作量约为 **2500+ 行侵入式修改**，且后续难以跟进上游更新。
   - 实现轻量自研控制器（TypeScript / Node.js）：基于 P0 沉淀的探针代码，核心状态机 + 账本 + 三端适配器总代码量预计在 **1200~1500 行** 之间，结构极为清晰，无第三方包历史包袱。
3. **经验与资产复用**：
   - 借鉴 Ralph Orchestrator 的结构化报告与看板展示。
   - 借鉴 DSH Ralph 的子任务有界报告约束（`maxHandoffChars`）。
   - 借鉴 Beads 的任务依赖图 ID 设计。
